## Trusted identity, writes and privacy

The browser calls only `/_api/serverlogics/appointments`. The endpoint obtains ActorContactId from the trusted `Server.User` Contact identifier, accepting the hosted lowercase `contactid` attribute and equivalent SDK GUID representations. It uses a fixed action/command allowlist and rejects client requester/owner/status/admin fields. Its role is Authenticated Users; anonymous users cannot use the endpoint. Direct `Webapi/mss_appointment/enabled` remains false. Ordinary portal read grants use Requester and Recipient Contact scope, with separate global Read for Administrators. No Appointments portal role receives direct Create/Write/Delete/Append permissions.

The unbound `mss_AppointmentCommand` API runs the Sandbox plug-in under its Dataverse integration caller, without SYSTEM elevation. It independently validates the active, login-enabled portal Contact, exact site's web roles and record participants. It returns only IDs/names for eligible recipient search, never identity secrets. Directory search and creation require an existing functional role. The separate `all` command requires the exact existing site Administrator role and permits broader reads. Personal incoming, outgoing and calendar commands always apply participant filters, including for administrators; responses on behalf of a recipient remain forbidden. ActorContactId is a trusted integration input, not an authentication claim for arbitrary callers; access to the underlying Dataverse API requires the integration caller's Dataverse privileges.

Create stamps Requester and Pending. Accept/reschedule requires the actual recipient, Pending status and matching row version. The final write uses SDK `UpdateRequest` with `ConcurrencyBehavior.IfRowVersionMatches`, so a race cannot overwrite a newer response. Requester, recipient and preferred time are immutable through response commands. See [backend source/build/registration contract](../backend/appointments/README.md) and [actual UAT registration IDs/hash](../scripts/appointments/action-registration.json).

The earlier hosted form-save verification confirmed trusted Requester, selected recipient, Pending status and the expected UTC instant; the record survived refresh. All five uniquely named verification rows across the two modules were then removed. The current view revision made no business-record writes. Its signed-in Administrator/Volunteer session now verifies the separation of personal and administrator reads, but does not prove separate ordinary-participant isolation or a live two-person acceptance.

## Time, calendar and rescheduling

Browser conversion uses `America/New_York`; server conversion uses Windows `Eastern Standard Time`. Both reject nonexistent spring-forward times and require selecting the matching offset for a repeated fall-back time. Dataverse stores the resulting UTC instant. The browser's timezone is never used for meeting input or appointment calendar day/time. The local browser checks deliberately ran in Asia/Riyadh. Historical New York offsets before 1883 can differ between Intl and Windows; the server rejects mismatches rather than silently saving a different instant.

Accepted appointments appear in My Calendar for either authorized participant using the original preferred instant. IDs are namespaced and deduplicated against Event/Meeting Invite items. No duplicate CRM/calendar records or external calendar sync is created. Opening the calendar, returning focus or making the tab visible refreshes only the Appointments source, aborting stale reads and replacing its items without reloading Events/Meeting Invites or changing the selected month. Pending, Cancelled, Rejected and unconfirmed proposals remain excluded.

Rescheduling writes the existing Rescheduled choice, reason and suggested instant to the same row, preserves preferred time, and exposes the reason, suggested time and **Proposal awaiting agreement** through the Rescheduled badge to both parties. The keyboard- and touch-accessible popover preserves the collapsed card height. It does not enter My Calendar. No confirmed requester-approval workflow was found, so this release intentionally provides no further confirmation transition. That workflow needs a separately agreed rule for recording the confirmed time.
