# Coverage upload repair

The user's existing Press Coverage File column remains the destination for attachments and publication logos. The working Meeting Report mechanism was reviewed: it sends larger requests to a separate Power Automate/SharePoint upload service and associates attachment rows with a Meeting Report. Coverage instead currently sends the whole base64 file to Power Pages Server Logic before server-side block upload. UAT reproduced successful 68-byte/100-KiB/1-MiB uploads and failures for larger requests (HTTP 400/500). The declared 2-MiB logo / 10-MiB attachment limits therefore cannot be satisfied by the current single-request transport.

Use bounded browser upload/download requests, preserving the exact saved coverage ID and existing file-only retry. Store native upload continuation state privately in one new nullable Memo column, `mss_coverageuploadstate` (16,000 characters), on the existing coverage table. This is an internal transport field, excluded from portal DTOs and forms, and is cleared after commit. No existing business data is repurposed.

A dedicated trusted SDK file command (`ActorContactId`, `Command`, `Payload` → `Result`) handles native file blocks, with a maximum 256-KiB decoded chunk. The server bridge obtains the actor from Server.User and performs the existing portal permission check; the command independently verifies an active identity and original Submitted By ownership or exact-site Administrator membership. Read operations require an eligible authenticated actor because coverage is already readable by all authenticated users. Direct table Web API stays disabled. Session tokens are never returned to browser code.

Upload state binds a random session ID to coverage ID, actor, variant, filename, MIME type, exact size and chunk hashes. Conditional RowVersion updates claim each operation before native file actions. A busy/committing claim prevents competing replacement sessions; abandoned state expires. Retry restarts only the file transfer on the existing record. Replacement commits only after all validated ordered blocks exist. The initial file signature and final total size are validated against the actual record variant. Stale or conflicting sessions fail safely rather than switching targets. Errors remain sanitized.

Downloads use bounded requests through a trusted fixed record ID; each block initializes an authorized native download internally, so native tokens stay server-side. A captured file ID/metadata must still match before each block to detect replacement during download. The browser validates the descriptor, exact block lengths, final signature and complete size before exposing the resulting Blob. Successful upload re-reads the committed file metadata and verifies its ID/name/size before reporting completion.

UI corrections already authorized by the user: hide a Pending appointment badge when Accept/Request Reschedule actions are shown; preserve other statuses. Activity uses a trash-icon button with accessible Delete Activity label, Pin/Unpin labels, and a styled Open button. Coverage rows expose a file download control tied to that row's ID.

UAT schema addition and dedicated action registration require user approval before application. Prepare source/tests independently, then deploy only the approved UAT target. Verify real PDF and PNG files near the 10-MiB and 2-MiB limits, replacement, retry on the same record, file readback hashes, unauthorized payload rejection, and no regression to existing reports or other modules. Use only uniquely named own test records and remove them afterward.
