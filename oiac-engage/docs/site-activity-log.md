# Site Activity Log backend

This implements a read-only exact-site history API, footer-only `/activity/history` page, and separate asynchronous observers. It reuses `mss_activitylog` (`mss_activitylogs`) and its existing active Event Key unique index. It changes no schema, existing business handler, record, environment audit setting, or automatic retention policy. The user added Deleted (866530017), verified read-only. Meeting Report attachment history was explicitly deferred: its service, flow and storage remain unchanged.

## Read contract

`POST /_api/serverlogics/site-activity-log` accepts `{ command: 'list' | 'detail', payload }`. The authenticated bridge derives `ActorContactId` from `Server.User`; unknown fields and browser actor arguments are rejected. It invokes `mss_SiteActivityLogRead` with `ActorContactId`, `Command`, `Payload`; the custom API returns a JSON string in `Result`.

List payload: `{scope:'mine'|'all',page:1,module:null,action:null,from:null,to:null}`. UTC/offset ISO timestamps are inclusive from, exclusive to. The native query applies website `e7f400bd-1e04-4efa-b8b3-7a7a3b168662` and own Performed By restrictions before count, ordering, or pagination. Only current membership of Administrators role `6ec72c3e-4f1b-420f-9565-d20047b12c1f` on that website permits `all`; Staff does not. Every detail request `{id,scope}` repeats authorization. Eligibility follows the existing enabled, active Contact and local/external identity checks.

List returns `{ok:true,entries,nextPage,totalCount,canViewAll}`; detail returns `{ok:true,entry}`. Entries contain `id,actorName,action,module,recordType,recordId,recordTitle,occurredOn,summary`, with `details` on detail. Errors are `{ok:false,error:{code}}`. Pages contain 25 rows ordered Occurred On descending then primary ID descending. The bounded page ceiling is 2500. The internal native `count` command is never browser-facing. The bridge invokes it separately after a successful list; count errors/Dataverse count limits produce `totalCount:null` without discarding entries or continuing SDK work inside a faulted transaction.

Direct history table Web API is explicitly disabled. The supplied permissions grant authenticated own Contact-related Read and exact Administrators Read only, with all mutation permissions false. Native queries independently enforce website isolation, including for administrators. Custom API execute privileges and integration application roles must remain restricted to trusted server identities; exposing these credentials would invalidate the trust boundary.

## Native capture

`SiteActivityLogNativeProvenancePlugin` runs at synchronous Stage20 while real custom API ancestry is available. It validates the exact implemented native API/command, typed actor and matching organization/user/initiating-user/correlation, allowing only bounded wrappers for the same row. It performs no SDK reads/writes, changes no Target data and never throws into the business save. It writes a fixed namespaced v2 SharedVariables receipt bound to record, table, message, site and identity context. `SiteActivityLogCapturePlugin` runs asynchronously PostOperation and accepts only that exact self-context v2 receipt. It never searches rewritten asynchronous ancestry or falls back to ancestor/browser ActorContactId parameters. The marker-only v1 canary receipt is not accepted. If supplied, SDK portal identity must agree with the actor. Target Contact/author is never substituted. A controlled hosted native SDK post demonstrated v1 synchronous-to-asynchronous receipt transfer; production v2 action delivery and browser actor attribution require their own hosted proof.

Supported projections:

- Activity post Create/post -> Published; comment/reply Create -> Created.
- Actual pin/unpin flag transition -> Updated; unchanged flags produce no event.
- Appointment Create/create -> Created; Pending -> Accepted -> Accepted; Pending -> alternative-time proposal -> Rescheduled, with `confirmed:false` and explicitly unconfirmed summary.
- Explicit Activity remove/delete -> Deleted only with `deletedAction=866530017` configured. Publication of this choice was separately verified by the coordinating task; this code does not publish it. Without configuration, deletion projection remains disabled.

Images contain only the minimal status/pin/parent fields needed for projection. Generated labels keep record titles below 100 characters and avoid copying user content. Actor name is bounded to 100, with a generic fallback for overlong names. Details are valid, allowlisted JSON below 4000 characters; no truncation, tokens, arbitrary content, links, or request bodies. Actor ID snapshots are canonical GUIDs and survive lookup removal.

`SiteActivityLogWriter` uses a SHA-256 key over website, actor, durable System Job operation ID, target and semantic operation. Its deterministic row GUID and pre-query/Create approach is append-only; there is no Upsert, duplicate Update, or browser append API. A concurrent unique-key/Create fault is retried as a whole asynchronous delivery, whose next pre-query sees the winning row. Failed delivery and missing images request Dataverse `OperationStatus.Retry`; after the platform's finite retries, operators must inspect/retry the failed System Job. Successful business mutations are not resubmitted to repair history.

The guard implementation registers on history Update/Delete for a verified Standard table. Standard existing-row Upsert calls Update and reaches that same guard; no unsupported/unfiltered Upsert step is registered. Permanent guard registrations remain disabled pending hosted Contact relationship-maintenance proof; source-level implementation alone does not establish active native append-only enforcement. It permits only a single-field change to the optional live Performed By relationship under a verified immediate native Contact Delete or Merge parent, matching organization/correlation and nested depth. Delete may clear only the current deleted Contact lookup; Merge may replace only the current subordinate Contact with its verified surviving Contact. The guard reads the original lookup to verify it, performs no writes, and fails closed on SDK errors. Actor ID/Name snapshots and every other history field remain immutable. Extra attributes, browser/maintenance flags, unrelated parents, wrong Contacts, or direct/root updates are rejected. Actual platform parent context and RemoveLink/Merge behavior still require hosted verification before activation. Archive behavior, retention/privacy operations and other maintenance paths require separate review; no general maintenance bypass or purge is included. Normal identities should have only the minimal native Create/Read and lookup Append privileges needed by the trusted writer; portal roles remain Read-only. This does not prevent a privileged platform administrator from changing registration/security.

`SiteActivityLogPortalActor.TryResolve` is available to a separate legacy observer. It uses `IPluginExecutionContext2.IsPortalsClientCall` and `PortalsContactId`, plus explicitly configured exact integration System User and organization IDs, depth 1 and no parent context. Candidate integration IDs are deliberately not defaults. Missing identity or nested cascades fail closed. Root-owned legacy capture code, if present, compiles into the same assembly; see its source/tests and coordinating report for coverage. Native technical coverage-file mutations and report-attachment flows are not inferred as successful uploads by this native observer.

## Build and registration

From the workspace root:

```powershell
& ./oiac-engage/backend/siteActivityLog/build-test.ps1
node ./oiac-engage/scripts/site-activity-log/bridge-test.mjs
```

The script compiles and tests a strong-named .NET Framework SDK plugin under `.superpowers/site-activity-log-build`, verifies its strong name, and separately compiles administrative helpers. It makes no network calls and does not invoke registration. Preserve the signing key for later assembly updates.

`RegisterSiteActivityLog.Apply(service,dllPath,manifestPath)` prepares the assembly/read API. Native `configure-native <assemblyId> <freshJournal> allow-mutation` preflights all metadata and journals IDs before adding disabled-only stamps, async observers and guards; it never overwrites existing components. `activate-native-capture <assemblyId> <freshActivationJournal> allow-mutation` verifies exact UAT, signed remote assembly content equal to the local reviewed DLL, all eighteen types/steps/images and handler ownership before activating only eight source + eight async steps. Permanent guards must remain disabled; legacy observers remain unchanged. Appointment Delete is an inert compatibility pair because the native API implements no delete command. Unexpected registrations using protected handlers, including temporary guard-proof steps, must be reviewed/removed first. Activation state changes are sequential; a failure stops and the journal supports reviewed recovery/resume. Published table metadata must explicitly say Standard before any registration/activation mutation; Elastic/unknown types are refused. Standard Upsert(existing row) calls Update, so the two scoped Update/Delete guard registrations protect existing history without an unavailable Upsert filter. Other unsupported table/message filters fail before journal/mutations with exact pair diagnostics. `diagnose-native-filters` is a read-only exact-UAT metadata command. `HistoryAdminHost` independently checks connected organization and WhoAmI, and mutation modes require the explicit acknowledgement. Administrative helpers alone do not authorize an environment change.

## Release gates and limits

Local fake-service tests prove query isolation, exact-site role checks/revocation, strict payloads, synchronous provenance/v2 receipt validation, actual actor attribution, scalar safe details, bounded snapshots, no-op suppression, deterministic retry handling and guard behavior. Bridge tests prove Server.User stamping, no arbitrary append, and independent count failure. They do **not** prove hosted identity propagation, image availability, asynchronous job persistence/retry, transaction rollback suppression, security role enforcement, or runtime connector envelopes.

Before enabling, demonstrate on approved UAT using two ordinary Contacts and an Administrator: preserved SDK/parent actor identity, root-versus-cascade behavior, expected images and stable operation identity, successful commit delivery, rejected/rolled-back mutation suppression, duplicate/retry behavior, failure monitoring, and own/admin list/detail/count isolation. Microsoft explicitly cautions that ParentContext values/order can change, so this is a deployment and ongoing regression gate. No module is claimed hosted-proven by this implementation. Actor deletion between business commit and asynchronous execution is an additional delivery limitation: the queued context still proves the actor ID, but retrieving the deleted Contact and creating its lookup can fail permanently. Existing saved snapshots are preserved; pending jobs are not claimed resilient to this race. Do not substitute the target Contact or fabricate actor attribution.

Environment-wide native auditing was disabled in the reviewed metadata and remains unchanged. This custom history is eventually delivered and can have a delay; it is not immediate transactional native audit. No historical events are backfilled, and no automatic purge is configured.
